# 行政区工程总规则

## 1. 来源与权威

唯一地点基准为 Overture `2026-10-21.0`。正式区的全部输入最终都有保留、归并、排除或待判去向。

每区 `行政区主档.md` 是唯一持续维护的主档，保存有效对象、已接受关系和任务。原始来源和机器底表只读；自动十表、索引、统计是派生结果。

`辅助记录.md` 的结构化处置表保存排除、归并、待判和退役对象，其余表保存证据、名称、实际覆盖及处置过程。

同一对象只在主档或辅助处置表的一处。状态变化时按合同移动，不形成第二套有效对象清单。散文备注不能覆盖固定字段。

旧地图、T1、旧铁路点表和美食名录不作为新地点输入。不要求逐旧 ID 清洗或旧保护数量守恒。

官方行政、地址、建筑形状和用途资料仅作辅助，不生成第二套 POI。区负责人可按第 5 节集中查找现成官方或可信非官方地理划分，建立结构片区；这不增加外部店铺等来源地点。逐店分拣的网络检索仍按第 2 节执行。

Overture 原始 `sources` 字段完整保留。它只追溯本源，不触发旧地图回连。

## 2. 小批分拣

区负责人先按第 5 节建立本区可用的片区框架，再把共同框架与本批有关的证据交给子 Agent。框架可随新线索完善，不等全区所有边界、性质都查清才开批。

| 项目 | 规则 |
|---|---|
| 默认批量 | 每个子 Agent 每批 50 个对象。 |
| 复杂批量 | 由区 AI 按复杂程度自行缩小，不设固定小批门槛。 |
| 本批完成 | 保存判断、采用字段、证据引用和待判项。 |
| 下一批 | 本批已保存后自动领取，不逐批等人确认。 |
| 全区覆盖 | 正常点也要处理，小批不是抽样。 |

脚本生成底表、自动预分类和复制源行不算已处理。

50 个是处理起点，不是已验证的最佳批量。每个区聊天只专注一区；出现仅凭无关词片机械套类、漏项或混关系时，由区负责人缩小复杂批次。只做有限核对，不新增固定审核轮数或逐店查证；正常辨名归类不属于机械套类。

本阶段优先速度、准确业态分类和地点子集。点位本身已有余量，不以尽量保住每个点为目标。

| 判断 | 直接处理 |
|---|---|
| 完整店名一眼能大致辨认业态 | 直接分类；大致相容的原类或合理宽类即可，不搜索。 |
| 店名与地址能辨认所属街区、商场、机场或景点 | 直接挂实际父对象，不搜索。 |
| 名字、位置、身份或归属有疑点 | 先看本地现有信息；公共信息不足、公众用途不明按第4节直接排除，其它冲突待判，不单独开网络调查。 |
| 完整店名仍不能判断大致业态 | 放进本批待搜组，每个未知对象只搜索一次，多个对象可集中检索。 |

小批搜索只为判断未知业态，每个未知对象只搜索一次，不逐个打开店铺页面调查。已有大致相容的分类或合理宽类就接受，不为更细分类追加检索；一次检索后公共信息仍不足、无法辨认公众用途的按第4节直接排除，其它身份或位置冲突标黄／红，不换词、换站继续查找。子 Agent 发现片区缺口交回区负责人统一核对，不各自建立冲突的片区框架。

每批只更新必要任务和待判记录，不重写整区大报告。不套正文五源六审。

## 3. 统一分类

分类入口为[分类树与标签目录](../共用/分类树与标签目录.md)。程序字典为同目录 `classification-contract-index.json`。

- `activeTreeCategories`：规范用途树。
- `materialTagCategories`：独立资料标签。
- `aliasOf`：同义旧分类 ID 对照，不重复展示。

分类以能服务写作的大致业态为准。完整名称一眼能辨认即可直接采用；与现有信息大致相容的原类或合理宽类都接受，不为寻找更细的类别追查或返工。只有仍无法判断大致业态时才按第 2 节搜索一次。自动预分类可以修改，不以细 token、关键词或法律类别设选类门槛。

主用途、兼用与外观风格分开。资料分类祖先与实际地域父对象也分开。

居酒屋等明确细类保留。taxonomy 祖先和 basic 不作为独立用途冲突投票。

名称可清楚说明本体用途；店名碎片、菜单、地址中的楼名不能代替本体判断。

分类树由中央整体维护。区负责人提供实际对象与缺类说明，不私造编号；用户举例不是白名单。

## 4. 保留与排除

先按公众用途和点位粒度筛选，再归纳保留对象子集。不为补齐树改变保留资格。

普通餐饮、住宿、商店不设代表配额、数量上限或服装白名单。普通服务不笼统删除。

| 正常使用 | 不因这些条件视为内部专用 |
|---|---|
| 消费、购票、普通预约 | 正常经营场所。 |
| 办事、就医、公众可申请租借 | 正常公众用途。 |
| 持票、安检等旅客准入 | 机场、车站等旅客空间。 |

员工、住户、内部作业、执勤空间按真实用途判断。主要政府机构与公众用途保留；内部科室、小柜台、执勤设备不冒充完整主体。

### 公共信息不足：直接排除，不退回再判（2026-11-01 用户确认）

**利用现有资料仍缺乏可用公共信息、无法辨认面向公众用途的点，按本工程逻辑视为写作重要性低，或倾向保密／内部使用，直接按非公共开放设施作 `exclude`。**无需取得“不对外开放”的明确证明，不先标黄等待重判，不为确认开放性追加搜索；只有业态未知才按既定规则搜索一次。

保留原ID、原行和“公共信息不足，按非公共开放设施逻辑排除”的简短理由后继续下一项。中央接受这种工程判断，**不得仅因缺少内部专用的确证而打回重判、补证或重新标黄**。这是写作筛选判断，无需追加现实准入认证。

完整名称或现有资料已经能辨明餐饮、零售、就医、办事、普通预约等公众用途时，照常保留；缺官网、缺详情或个别字段缺失不单独触发本条。身份、位置及疑似同体冲突仍按各自规则处理。本次规范更新不自动重开已审收区或清理旧待判库。

机场、交通枢纽、景点及其它公共设施同类同理：

- C 门、B 入口等纯编号门、出入口、跑道和纯通行／运行点继续排除。
- 休息室、店铺等合格独立用途保留，挂实际所属设施。
- 排除保留原行、原因和依据。
- 按对象本体判断，不按“门／入口”等名称关键词硬删。

低分、缺字段或无坐标本身不触发自动排除。闭店、迁址、改名与从未存在分别判断。

### 后续新增点位：服务设备与吸烟点（2026-11-01 用户确认）

从本次拍板后的首次分拣、新增收纳起，以售票机、自动贩卖机、ATM、取件柜及类似无人值守自助服务设备为本体的点位，原则上按 `exclude` 处理。吸烟点也排除，包括仅以吸烟区或吸烟室为本体的独立点位。保留原行及“服务设备／吸烟点，按写作粒度排除”的理由；举例不限定同类设备范围。

既有对象仅按 2026-11-01 用户另行点名的范围处理：本轮 4 个纯品牌名 `セブンティーンアイス` 贩卖机转为 `exclude`，保留各自原 ID、原行与排除理由；这不表示它们是重复源，也不按品牌字符串全库清退。其它既有已采用设备及其内部链暂不回溯，不因规则更新自动改名、清退或重建已有成果。

按对象本体判断，“无人值守”不作为一律排除完整店铺、停车设施或其它独立场所的关键词。

### 可疑对象：按写作尺度止查

当前工程服务写作。可疑点不必穷找来源，也不必查清现实身份才能作出取舍。

| 情况 | 本批处置 |
|---|---|
| 公共信息不足，现有资料或一次业态检索仍无法辨认公众用途 | 直接按非公共开放设施逻辑排除，留原行和短理由，不退回再判或补证。 |
| 已能辨认公众用途，但具体身份、位置等仍有冲突 | 标黄或红，停止查找；不继续换词、换站追查。 |
| 附近已有疑似同对象，可能只是另一种写法 | 优先标红、倾向弃置。记疑似对应 ID，无须先证明完全同体，也无须为标记另作搜索。 |
| 明确分店名、分寺名或现成资料已能区分不同主体 | 分别保留；不因同品牌、同宗派或距离近自动收拢。 |
| 商场与店铺、寺院与独立子设施等真实父子对象 | 按层级处理，不能仅凭名称包含或距离近认作重复。 |

- **黄：暂挂。** 当前线索不足，停止本轮查证，后续可能弃置。
- **红：倾向弃置。** 可疑冗余或身份指向过弱，供中央汇总取舍。
- 区 AI 按现有信息选色，不设搜索次数竞赛、固定距离或概率阈值。
- 两色均记录原 ID、原行、简短原因及已有线索。未搜索时如实写明，不伪造搜索或证据。
- 对象先记 `pending_review`，关联 `open` 问题，放辅助处置表。标记后继续下一项，不要求本批必须解开疑点。
- 中央后续可按写作尺度采用 `exclude`，理由写“写作尺度弃置／可疑冗余”。不用先证明现实不存在或完全同体。

这项取舍不等于普遍挑选代表店。正常有效对象仍按实际层级全量归挂。

没搜到不证明现实不存在；近邻疑似重复不证明现实同体。两者都允许立即止查和提出弃置意见。只有实际确认同体时才记录同体归并，原始资料始终保留。

不放到车站或行政中心占位。逐店集中搜索只处理本源未知业态，不另开外部 POI 补库；区级地理划分依据按第 5 节另行集中处理。

## 5. 区负责人切片与范围依据

中央统一划分口径、共用资料入口和分类词条，协调跨区 owner，有限审收；区负责人负责本区切片、维护框架和归挂，不逐片等待中央审批。

本阶段把行政区按可用于写作和程序展开的小片组织起来，优先收纳、逐层归挂，主动减少大量具名地点在同级直接堆放。区负责人建立可用小片框架后，按大体位置及写作关联就近吸纳，无需逐点证明精确片区边界或官方归属。同一个源点保持唯一，不因归入不同小片复制点位。行政区本身不能代替生态街区；片区可以包含多个街道、通及不同用途，允许混合性质。已有官方或可信地方划分可作为框架参考，地址与现有地理资料够用就直接批量归挂。

| 参考材料 | 采用方式 |
|---|---|
| 市区官网的地区划分、町名地名、区域规划、地区介绍和地图 | 读取实际名称、范围与划分用途；行政所管、规划用途不自动等于生活街区。 |
| 观光协会、商店会及可靠地方资料中的片区图、街道范围 | 核对材料实际说明的范围、所属与边界，保留出处；非官方不等于不能采用。 |
| 地址、现有地理记录、建筑或设施资料 | 按大体位置就近组织小片；地址相近不自动证明设施内部或同体。 |

上述资料帮助形成可用框架，不要求每个归入小片的点都取得精确范围或官方归属证明。小片及周边区域可用合理工程组织名称，简要说明大体位置和采用方式，不冒充官方专名。统计局的立地环境、国交省的用途分类只供性质词条参照，不直接当作片区边界。

新生态街区及更小片区自然使用可辨地点、业态或生态名称，可写“○○一带”“○○周边”“○○附近”“○○圈”“××至○○周边”等，避免过多街道名、地点名堆叠即可，不硬性限制地名个数，也不为命名另开调查或返工已有合理结果。已有实际可辨的官方名可以复用；办公区、工业区等用途或生态命名仍须有依据，不猜人群或用途。“高层建筑群”等学术性或纯外观概括不作新片区名，建筑高低、材质和形态只挂性质词条。本条不改真实街道、商业街、桥梁或其它设施本体的合法名称。

区负责人集中取得这些可复用依据；资料已足以划分和归挂就使用，不以穷尽来源、精确重画多边形或全区零待判为目标。注明实际采用的来源与版本，分清资料原有划分和工程中有依据的组织方式。

生态、建筑、商业及社群性质使用已有相应词条。有现成依据时顺便标注，不开展穷尽社群或全属性调查。性质鲜明本身不自动产生新片区；更小区块的组织规则见第 6 节。结构片区的用途分类可暂空，名称及位置记录说明采用方式，不要求逐点精确归属证明。

片区框架以主档结构对象和关系为准。区负责人维护 `area_partition` 任务及实际对象范围，给子批同版框架；子批返回新线索，由负责人合并后再向后续批次提供。收尾时核对跨批归属与剩余范围问题，不另建第二份片区正本。

### 位置与未定范围

采用原经纬度及注明版本的地理依据。旧画布坐标不参与判断。新定位、精确坐标和多边形不是本阶段必交项，也不是写作信息的前置要求。

位置需修正时保留原值、采用值、原因及证据引用。没有依据的继续待判，不猜坐标。

生态街区、行政町丁目与具体商业街分别辨认。行政面、地址代表点和规划用途不自动等于实际街区范围。

不强行把生活区归成商业街，也不把重画全区精确多边形作为所有归属前置条件。

已有可用小片时按大体位置及写作关联就近吸纳，不因精确边界未证实而搁置整组归挂。确有未解决对象或冲突时记具体待判和下一动作，不把写作归挂冒充官方精确划分，也不借此改动源点坐标。

## 6. 全量层级子集

普通有效对象不选代表。按第 4 节完成疑点取舍后，全部保留对象按真实结构归纳。

| 上层 | 直接子集举例 |
|---|---|
| 生态街区 | 可用的更小片区、具体商业街、综合设施、其它街道或独立地点。 |
| 较小片区 | 按大体位置和写作关联就近吸纳的地点或已有设施链。 |
| 综合商场 | 内部店铺与设施。 |
| 具体商业街／其它街道 | 实际所属路段内的地点，可包含综合设施。 |
| 店铺 | 实际内部且符合保留资格的小设施。 |
| 机场 | 航站楼及实际内部设施。 |
| 景点／园区 | 真实内部区域、场馆或设施。 |

只记录直接父，上层全部子集沿成员图汇总。不把叶子打平成街区直系成员，不重复挂祖先。

“○○一条街”“某街周边”“某站周边”、商业街和综合设施只是可用层级的例子，不是必填清单。积极使用可用小片就近吸纳并逐层归挂，让地点尽量被收纳，展开时带出相关下级，减少同级具名点堆放。层数随组织需要确定，不设固定半径或孩子数量；同一个源点不因多个小片重复创建。一句话介绍仍留作后期空位。

已有商业街、综合设施、店铺及小设施的内部链继续复用；外围点就近吸纳进周边小片，不塞进本体内部。写作小片组织与精确物理容纳分别说明，“某站周边”不等于车站内部。无需为了周边小片逐点重查官方边界或内部链。

源对象实际作父时，由区 AI 明确父类型：district、life_area、street 或 facility。普通叶子不增加此字段义务。

区域对象沿用 kind。用途分类不决定容纳结构，也不默认所有源父都是设施。

同一源主体不另造同体结构父。已有真实父优先复用稳定 ID；旧精选名字不能直接成为已接受父对象。

完整地址和楼名相符且无矛盾，可整组判断同楼成员。同丁目、短号或数字相似不足以证明同楼。

## 7. 关系与身份

| 关系 | 用途 |
|---|---|
| district_member | 街区、生活区或具体街道的直系成员。 |
| facility_member | 实际设施父对象的直系成员。 |
| related | 实际非包含关联，不重复成员边。 |
| 同体关系 | 单独记录身份去向，不能用成员关系冒充。 |

包含关系无循环。related 可以双向；不恢复距离和数量配额。

改直接父或父类型时，退休被替代的自动边并保留历史。跨区主体只有一个写入 owner，其它区引用。

同名、异名和近邻只需形成可疑线索，不强制完成现实同体考证。疑似重复先按第 4 节标黄／红；写作弃置与确认同体归并分开。

## 8. 名称与内容

全区扫描原名、异名、片假名、异体字、不同写法及来源已有拉丁拼写。

记录原字段或实读依据，以及品牌泛名、具体分支、主体别名、历史名等角色。原始写法只读，不自动翻译、转罗马字或统一换字。

### 分店、分寺必须能辨认具体对象

| 情况 | 工程识别名 |
|---|---|
| 已有完整分店、分寺或院名 | 优先保留完整名称及必要分支限定；已有“○○店／支店／別院”等全名不硬改后缀。 |
| 只有品牌、但本源已有可靠分支所在地 | 写成“品牌＋○○分店”，不能只拼“品牌＋裸地名”。 |
| 寺院分支需要补充识别 | 写成“寺名＋○○分寺”，或有依据的具体“○○寺／别院”完整名；不只接裸地名。 |
| 名字或分支仍不明确 | 不编官方店名、寺名，不拼整段长地址。按第 4 节标黄／红并止查。 |

工程识别名放主档或辅助处置表的 `name`。来源原名留在只读原行；自行组成的工程名在辅助字段注明角色与依据，不能冒充官方名。

纯品牌只作搜索线索，不能单独触发具体分店。工程识别名和名称候选均不自动变成运行显示名、采用异名或激活词。

附近已有疑似同对象时按写作尺度标记，优先考虑冗余弃置。现成信息明确区分的分店、分寺、同名独立地点分别保留；共享品牌、泛别名或旧合并名称池不当作已证实同体。

自动名称扫描只证明原写法已收齐。具体分支和可疑重复由本批判断或黄／红记录承接，不以自动扫描冒充已消歧。

旧精选名字只是后期下潜线索。日本全域／东京大舞台一句话及旧详情是内容资产，不带回旧地址、坐标、分类或关系。

正文、一句话、名称统一、地区搜索、资料搜索及后期公共项目下潜另期处理。空正文不是当前分拣缺口。

## 9. 版本与接力

多人分区使用同一 Skill、总规则、字段合同与分类版本。区内不另加限制。

主档记录领取版本。中央 6astra 统一派发、归纳和收货；独立区聊天由 6.1sol 负责整区，可用 3 个子 Agent 并行小批。

按实际 GPT 容量动态安排 2—3 个或更多区。推理强度由中央决定，不固定并发队列，不混算区聊天和子 Agent 槽位。

在已授权范围内自动续源对象小批，直到全区输入都有明确去向；区负责人另收尾片区框架、归挂和跨批合并任务。领取不等于完成；同区由负责人合并结果，避免子 Agent 同写重叠对象。

自动收货仅是候选成果。用户与中央共同判断后才启用，不自动写入运行库。辅助材料和自动索引不维护另一套任务完成结论。

原输入和相关规则未变，可复用已审判断。只有受影响项重开，不因整体指纹变化重查所有对象。

后续更新只承接本 Overture 工程自身历史。缺席对象、旧边、旧写法都保留去向，不拿旧地图作 base。
