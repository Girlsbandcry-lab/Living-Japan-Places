# Markdown 主档字段参考

字段名采用程序固定短键，下面给出中文含义。对象名称、说明、原因及正文备注可用中文和日文。

人和区 AI 维护两份 Markdown，不直接修改 JSONL。AI 可以用专用脚本批量编辑 Markdown 表格，仍以保存后的两份文件为准。

## 1. 固定位置与文件

正式工作目录相对仓库根：

`工程表/行政区重建/整区/档案/{行政区代码}/工作/`

| 文件／目录 | 用途 |
|---|---|
| 行政区主档.md | 当前有效对象、已接受关系、元信息及任务。 |
| 辅助记录.md | 其它对象去向、证据、待判、名称和覆盖。 |
| .baseline/ | 初始化时承接的只读底表和原始来源引用。 |
| 回货内 authoring/ | 当次受审 Markdown 原文快照，不再维护。 |

同一对象 ID 只能出现在主档 objects 或辅助 dispositions 中的一处。改变状态时移动整行，不复制另一份。

初始候选即使显示 keep，也不代表已经人工分拣。源对象完成程度看实际 coverage，片区框架工作另看任务结果；两者均不能由底表生成替代。

## 2. 表格格式

- 文件采用 UTF-8。
- 保留程序生成的表头及 `lj:table`／`lj:end` 标记。
- 同一表可以分段，重复表头；对象行不得重复。
- `∅` 表示无值。空白文字不是删除指令。
- 单元格中的竖线写作 `&#124;`，换行写作 `<br>`。
- 长引文和解释放辅助记录，不挤进地点字段。

表格外的短说明可以修改，程序会保留；它不覆盖固定字段中的决定。

## 3. 元信息 meta

表头为 `key`、`value`。由 init 生成，负责人不改指纹来绕过检查。

| key | 中文含义 |
|---|---|
| format | 固定格式 living_japan_markdown_v1。 |
| baseSnapshot | 本档只读基线，默认 .baseline。 |
| baseRevision | 初始化所承接的工作版本。 |
| receiveBaseRevision | 中央领取版本；与工作版本分开。 |
| ownerAdminId | 唯一行政 owner。 |
| officialCode | 行政区代码。 |
| sourceRelease | 固定 Overture 发行版。 |
| rulesSha256 | 机器规则指纹。 |
| classificationSha256 | 分类合同指纹。 |
| workflowSha256 | 共用 Skill、流程、规则及相关程序的综合指纹。 |
| claimId | 中央派发领取记录。 |
| operator | 本区负责人。 |

共同版本变化时由中央协调再续接，不由各区改指纹继续跑。

## 4. 地点 objects／dispositions

两表列相同。主档 objects 保存 source 的 keep 与 area 的 accepted；其余状态放辅助 dispositions。

| 字段 | 中文含义 |
|---|---|
| id | 稳定对象 ID。源对象来自正式 Overture 底表。 |
| recordType | source 为来源地点；area 为真实结构区域。 |
| name | 当前工程识别名。完整分店／分寺名优先；派生名须有依据，原始名仍保留在只读原行。不自动改变运行显示名或激活词。 |
| entityKind | 父类型：district／life_area／street／facility。源对象实际作父时需要，叶子可无值。 |
| categoryId | 同版分类合同中的用途 ID。source 的 keep 仍须有有效分类；结构 area 可用 ∅ 暂空，有值时必须有效。 |
| ownerAdminId | 实际写入 owner。跨区只有一个 owner。 |
| state | source：keep／merge／exclude／pending_review；area：accepted／candidate／pending／retired。 |
| locationMode | source 沿原值；corrected 有据修正；unknown 尚不明确。 |
| latitude | 采用纬度；不是旧画布坐标。 |
| longitude | 采用经度。 |
| address | 采用地址。 |

沿原位置时无需重复抄写坐标。修正必须保留原值，并在辅助 fields 中记录原因及证据；原始 raw 行不变。

名称未知、分类待判和位置未知分别记录，未知坐标不能移到行政中心占位；写作小片可以按大体位置及写作关联就近归挂，不因此改源点坐标。

结构片区使用 `recordType=area`，稳定 `geo:` ID 按同版程序的 owner、kind、永久键生成。`area-entities` 的 `nameEvidence`、`geographicEvidence` 保存已有名称、地址、大体位置及采用方式，说明这是写作小片的就近组织，不要求逐点官方精确归属证明。已采用者放 objects，候选或待判放 dispositions；尚未形成对象的线索可留 area-leads。

生态街区及较小片区的 name 自然使用一带、周边、附近、圈等合理工程名称，避免过多地名堆叠，不硬性限制地名个数，不为命名另查或返工合理结果。已有官方名可复用，办公区、工业区等用途／生态名须有依据。“高层建筑群”等纯外观或学术性概括不作新片区名，建筑高低、材质、形态只挂性质词条；真实街道、商业街、桥梁或其它设施本体的合法名称保留。仍有未解决对象或冲突时保存具体待判，不仅因精确片区边界未证实搁置就近归挂。

生态街区及周边小片选 life_area，具体街道／商业街选 street，实际设施选 facility；层级不由 categoryId 推导。“某站周边”与车站设施本体分开，既有内部链继续复用，外围点就近吸纳进小片。同一个源点保持唯一，结构片区不要求新增精确坐标、多边形或逐点边界证明，具体规则见总规则第 5、6 节。

## 5. 关系 relations／other-relations

主档 relations 只放 accepted；待判或 retired 放辅助 other-relations。

| 字段 | 中文含义 |
|---|---|
| id | 稳定关系 ID，不是地点 ID。 |
| fromId | 子对象；related 时为关联起点。 |
| toId | 直接父对象；related 时为关联目标。 |
| kind | district_member／facility_member／related。 |
| status | accepted／pending_target／pending_review／retired。 |
| reason | 关系依据的简短说明。 |

直接父以成员边为唯一记录入口。程序据此生成 assignments.parentIds 和区域 parentIds，不重复手填另一套父链。

只写直接父，不造祖先边。related 仅作非包含关联。改父或父类型时保留被替代旧边的退休历史。

## 6. 任务 tasks／task-objects

任务分别记录源对象分拣、区负责人片区框架或后期公共项目下潜。下潜任务存在不表示已经处理正文。

| tasks 字段 | 中文含义 |
|---|---|
| id | 稳定任务 ID。 |
| theme | 任务主题；源对象分拣用 sorting，区负责人片区框架与归挂汇总用 area_partition。 |
| round | 本次工作轮次。 |
| owner | 实际负责人或子 Agent 标识。 |
| status | planned／working／pending_review／completed／deferred。 |
| nextAction | 下一动作。 |
| resultRef | 实际结果入口；completed 时必填。 |
| replacesId | 接续或替代的旧任务 ID；旧任务保留。 |

`task-objects` 只有 `taskId` 和 `entityId`，明确任务对象范围。不要在备注里另藏一份不同清单。

片区任务关联主档或辅助 dispositions 中实际存在的片区、候选片区或相关源对象 ID；area-leads 线索 ID 不冒充对象 ID。框架初建时可关联所处理的源对象范围，采用片区后补齐实际相关对象。结果引用本区主档与辅助证据，注明所据主档版本、已归挂范围、跨批合并及明确剩余项，不另建第二份片区正本。

area_partition 状态由区负责人按本轮实际工作维护，不能由 sorting 批次清空或 source coverage 自动推成 completed。明确待判可保留，任务 completed 仍须有本轮范围的实际结果入口。

领取不是完成。明确待判可作为本批处置结果，但不能声称地点事实已经确认。

## 7. 辅助记录各表

这些结构化表是本档的辅助部分；同一事实只保存一处。散文备注不作为额外机器指令。

| 表 | 主要固定列及含义 |
|---|---|
| dispositions | 与 objects 同列，保存排除、归并、待判及退役对象。 |
| other-relations | 与 relations 同列，保存待判及退役关系。 |
| assignments | id、status、reason、issueRef：归属处理状态及问题入口。 |
| identity-mappings | id、targetId、action、reason、groupId：本 Overture 工程自身身份去向。 |
| name-candidates | id、entityId、originalWriting、status、sourceField：只记录原写法及来源字段。 |
| issues | id、entityId、status、problem、nextAction：真实待判问题。 |
| coverage | id、stage、status、method：实际处理阶段、状态与方法。 |
| area-leads | id、name、status：未确定区域线索。 |
| fields | table、id、path、type、value：证据及未压进主表的补充字段。 |

assignments 状态为 assigned／pending／not_applicable。已处理仍 pending 时，要关联真实 open 问题。

coverage 的阶段为 screening、classification、geography、membership、names。对象范围、所用规则及证据在 fields 中承接。

coverage 只能记录实际判断或合法复用。领取、自动预分类和批量复制不能直接记 completed。

现有 coverage 统计源对象各阶段处置，不代替区级 area_partition 任务；结构片区不加入 Overture 源分母。性质暂空不表示地理范围未判，二者分别保存。

名称候选仅收集，不赋予已采用异名或独立激活资格。被排除、归并对象的原写法仍保留。

自动 names 覆盖只证明原写法已扫描，不代替分支识别或疑似重复判断。

fields 的 type 使用 object／array／null／number／boolean／string。path 定位原结构字段；证据可引用原行或本地文件及指纹。

字段拆装优先用专用读写函数完成，不手工伪造层级、来源指纹或原始字段。源码中的 raw、rawRef 等只读字段由 .baseline 承接。

### 写作尺度标记与工程名

复用现有表及 fields，不增加颜色状态或第二份对象清单。

| 所属表 | path／字段 | 用法 |
|---|---|---|
| decisions | /nameRole | 自行组成工程识别名时写 string：engineering_label。 |
| decisions | /nameBasis | string：说明采用哪个现有分支、地址或设施字段；已有证据仍用 evidence 引用。 |
| issues | /triageColor | string：yellow 或 red。只记录本次写作取舍。 |
| issues | /suggestedDisposition | string：defer（暂挂）或 exclude（倾向弃置）。 |
| issues | /candidateTargetId | string：已有疑似对应对象 ID；没有明确候选则省略。 |

fields 的 id 指向所属表中已有的行 ID。nameRole 只标识工程名，不赋予官方名或激活资格；纯品牌不能代替具体分店名。

黄／红对象放 dispositions，state 为 pending_review；关联 issues 的 status 为 open。problem 写简短疑点，nextAction 写“停止本轮查证；交中央汇总取舍”。查询线索或未搜索原因写已有证据与说明，不伪造实读。

若另记 identity-mappings，同一疑点仍须关联 open 问题，不能只写 same_entity_candidate 就视为已解决。两色可作为本批已经处理的结果；未判断的分类、位置和父对象继续明确待判。

中央决定弃置后可改 exclude，并保留写作取舍原因和旧标记。不能把这个动作记成已确认现实同体或不存在。

## 8. 程序入口

程序为 `scripts/overture/district_archive.py`。以下供 AI 使用；用户不需手工执行命令。

| 子命令 | 参数与责任 |
|---|---|
| init | --base 底表目录、--output 工作目录；可填 --claim-id、--operator。已有目录不覆盖。 |
| next-batch | archive 目录、可选 --size；只看下一批，不领取也不记完成。 |
| claim-batch | archive、--worker；默认 --size 50。领取互不重叠的小批，已有同 worker 任务则续原批。 |
| finish-batch | archive、--task-id；检查本批实际覆盖已保存后结束该批。 |
| check | archive；核主档、辅助结构及派生检查。 |
| build | archive、--output；中央主审后才可用 --root-reviewed 形成受审候选。 |

每个子 Agent 默认 50 个对象。复杂批次由区 AI 自行缩小，不设固定小批门槛。

小批按区负责人提供的共同框架归挂。完整店名一眼能大致判业态、店名与地址能判归属，就直接处理；分类接受尺度与未知业态只搜索一次的停止线统一按总规则第 2、3 节执行，仍无法判断则标黄／红并续批。区级片区划分依据由负责人按总规则另行集中核对。

区负责人统筹最多 3 个并行小批，合并两份 Markdown 后提交 finish-batch，再自动 claim-batch。不逐批等人确认。

claim-batch／finish-batch 管源对象小批，不自动判断片区任务完成。源对象全部有去向后，区负责人同时核片区框架、跨批归挂与明确剩余项，再提交中央分别审收两条结果。自动收货仍是候选，用户与中央 6astra 共同判断后才启用。
